# 1. Цель проекта

FS_Template — это универсальная основа для коммерческих CRM-систем.

Мы создаём не одну конкретную CRM, а платформенное ядро, на базе которого можно разрабатывать специализированные продукты.

Примеры будущих решений:

- CRM для розничных магазинов и торговых сетей.
- CRM для алкогольных магазинов.
- CRM для интернет-магазинов.
- CRM для управления заказами, персоналом и клиентами.
- CRM для других направлений бизнеса.

Основная задача — создать надёжное ядро, которое будет использоваться повторно без необходимости заново разрабатывать авторизацию, безопасность, роли, филиалы и управление пользователями.

## 1.1. Бизнес-модель

Предполагается SaaS-модель с подпиской.

Целевые рынки:

- США;
- Европейский союз;
- Украина.

Оплата подписок — Stripe, с автоматическим продлением.

После неуспешной оплаты предполагается льготный период 7 дней.

## 1.2. Архитектура размещения

**Один клиент = один изолированный VPS = одна установка CRM = одна Organization.**

Это принципиальное архитектурное решение.

Внутри одной Organization может находиться:

- несколько филиалов;
- большое количество сотрудников;
- несколько бизнес-направлений;
- множество клиентов, заказов, задач и других сущностей.

Данные разных клиентов не должны находиться в одной общей базе CRM.

Позже будет создана центральная управляющая система для контроля клиентских VPS, подписок, обновлений, резервных копий и лицензий.

# 6. Пользователи, роли и права

## 6.1. Базовые роли

- OWNER.
- ADMINISTRATOR.
- MANAGER.
- EMPLOYEE.
- VIEW_ONLY / READ_ONLY — проверить актуальное имя в Prisma.

Одна установка CRM имеет одного первоначального владельца.

В будущем OWNER сможет создавать пользовательские роли.

## 6.2. Правила назначения

- OWNER управляет ролями и правами.
- Только OWNER назначает ADMINISTRATOR.
- ADMINISTRATOR назначает роли ниже себя.
- MANAGER может назначать только разрешённые владельцем роли.
- Пользователь не может назначить право, которого не имеет сам.
- Менеджер управляет только сотрудниками разрешённых филиалов.
- Расширение прав роли требует индивидуального подтверждения для затрагиваемых пользователей.
- Сокращение прав должно применяться немедленно.

## 6.3. Индивидуальные права

Предусмотрены:

- права роли;
- индивидуальные переопределения прав пользователя;
- проверка прав на backend;
- привязка ролей к Organization.

## 6.4. Существующая RBAC-схема

Последняя применённая до Bootstrap миграция RBAC:

```text
20261108151035_add_rbac
```

Созданы сущности:

- roles;
- permissions;
- role_permissions;
- user_permission_overrides.

В User предусмотрены старая enum-роль и новая ссылка `role_id`.

Это переходная архитектура.

**Нельзя без анализа удалить старое поле роли или начать использовать новую систему прав во всех guards.**

Сначала необходимо проверить реальную реализацию и спланировать миграцию существующей логики.

# 7. Филиалы

Одна Organization может содержать много Branch.

Сотрудник может принадлежать нескольким филиалам.

Роль и права сотрудника одинаковы во всех филиалах, но область доступа ограничивается назначенными филиалами.

Менеджер может управлять сотрудниками только внутри своих филиалов.

Если сотрудник потерял доступ ко всем филиалам, его доступ к CRM должен быть запрещён.

Первоначальное создание OWNER не должно требовать существования филиала.

**Первый филиал создаётся после завершения Bootstrap и входа владельца.**

Это согласованное решение.

# 8. Регистрация сотрудников

Обычный сотрудник не должен самостоятельно становиться OWNER.

Базовый сценарий:

1. Пользователь регистрируется.
2. Подтверждает email.
3. Получает статус PENDING.
4. Руководитель рассматривает заявку.
5. Назначает разрешённую роль и филиалы.
6. Пользователь получает доступ после подтверждения.

При регистрации сотрудника требуются:

- имя;
- фамилия;
- email;
- пароль;
- телефон;
- филиал.

Для первоначального OWNER используется отдельная процедура Bootstrap.

Обычную регистрацию и первоначальную регистрацию владельца нельзя смешивать.

## 8.1. Отклонённые заявки

Предусмотрены:

- причина отклонения;
- ограничение числа повторных заявок;
- настраиваемый лимит;
- разблокировка владельцем;
- после разблокировки — ограниченное число новых попыток.

Точные правила требуют сверки с актуальными решениями и кодом.

# 9. Двухфакторная аутентификация и Passkeys

Это согласованные требования, а не утверждение о завершённой реализации.

## 9.1. MFA

Обязательная двухфакторная защита для:

- OWNER;
- ADMINISTRATOR;
- сотрудников, управляющих правами других пользователей.

Для остальных сотрудников MFA может быть необязательной.

## 9.2. Passkeys

Планируется поддержка WebAuthn / Passkeys.

Passkey может заменить ввод пароля и TOTP при входе, если реализована корректная проверка WebAuthn.

Для чувствительных операций требуется повторное подтверждение личности.

## 9.3. Восстановление

Ранее согласовано:

- резервные recovery codes не выдаём;
- самостоятельное восстановление пароля — через подтверждённый email;
- при потере всех Passkeys и TOTP требуется отдельная процедура восстановления через руководство;
- изменение пароля, email, Passkeys или MFA сопровождается завершением необходимых сессий и email-уведомлениями.

Для первоначального OWNER нужна отдельная процедура аварийного восстановления, поскольку над ним нет другого руководителя.

**Эту процедуру ещё необходимо спроектировать. Нельзя автоматически считать email достаточным основанием для восстановления полного доступа OWNER.**

# 10. Политика блокировки входа

Согласованные требования:

- учитываются ошибки пароля и MFA;
- после трёх ошибок вход блокируется;
- активные сессии пользователя завершаются;
- разблокировка выполняется уполномоченным лицом;
- суточный счётчик ориентируется на часовой пояс организации.

Здесь есть важный нюанс безопасности.

Нельзя допустить, чтобы любой злоумышленник мог без ограничений блокировать чужие аккаунты, отправляя неправильные пароли.

Поэтому при реализации необходимо отдельно оценить:

- rate limiting;
- защиту от DoS через блокировку учётных записей;
- ограничения по IP и учётной записи;
- безопасную процедуру разблокировки;
- конкурентное обновление счётчиков.

# 12. Bootstrap — главная текущая задача

**Именно на этом этапе мы остановились.**

Bootstrap — безопасная процедура первоначального создания организации и первого OWNER на новой установке CRM.

Проблема, которую решаем:

На чистой установке нет ни организации, ни владельца.

Обычная регистрация не должна позволять кому-либо назначить себе роль OWNER.

Поэтому нужен отдельный одноразовый механизм первоначальной инициализации.

## 12.1. Согласованный сценарий

1. Администратор получает доступ к VPS.
2. Запускает локальную CLI-команду.
3. CLI генерирует криптографически стойкий одноразовый токен.
4. В PostgreSQL сохраняется только хеш токена.
5. CLI выдаёт защищённую ссылку.
6. Ссылка действует 15 минут.
7. Будущий владелец открывает страницу первоначальной регистрации.
8. Указывает данные организации и владельца.
9. Подтверждает email.
10. Сервер проверяет токен, сроки действия и состояние установки.
11. В одной транзакции создаются Organization, роль OWNER и пользователь.
12. Bootstrap переводится в COMPLETED.
13. Повторная первоначальная регистрация запрещается.
14. Владелец проходит обязательную настройку MFA/Passkey.
15. После получения полноценного доступа создаёт первый филиал.

Нужно уточнить порядок включения MFA относительно выдачи полноценной сессии.

**Нельзя выдавать OWNER полный административный доступ до завершения обязательной настройки MFA.**

## 12.2. Почему именно CLI

CLI запускается локально на VPS.

Не требуется создавать публичный endpoint для генерации первоначального OWNER-токена.

Это уменьшает поверхность атаки.

Команда должна использовать существующую конфигурацию базы и работать без запуска обычного HTTP-сервера.

## 12.3. Генерация токена

Предлагаемый механизм:

- `crypto.randomBytes(32)`;
- кодирование base64url;
- SHA-256 для хранения хеша;
- срок действия 15 минут;
- одноразовое использование;
- запрет повторной выдачи после завершения установки.

Сырой токен нельзя сохранять в PostgreSQL.

Необходимо избегать записи токена в обычные логи.

Если токен помещается в URL, требуется учитывать утечки через browser history, Referer, аналитику и сторонние ресурсы. Нужно предусмотреть безопасное погашение токена и политику `Referrer-Policy: no-referrer`.

## 12.4. Повторная выдача

Если первоначальный токен истёк до начала регистрации, CLI может выпустить новый.

После COMPLETED повторная выдача запрещена.

Повторная выдача должна инвалидировать старый токен.

Необходимо предусмотреть конкурентные запуски CLI.

## 12.5. Регистрация OWNER

Временные данные регистрации хранятся отдельно от обычных пользователей.

Пока email не подтверждён и процесс не завершён, полноценного OWNER ещё нет.

При истечении срока регистрации необходимо безопасно аннулировать или заменить временную заявку.

Пароль должен хешироваться через существующий Password_Service.

Email подтверждается отдельным одноразовым токеном.

# 19. Критические требования безопасности Bootstrap

## 19.1. Конкурентные запросы

Недостаточно проверять:

```typescript
if (setup.status === "COMPLETED") {
  throw new ForbiddenException();
}
```

Два параллельных запроса могут одновременно пройти такую проверку.

Необходимо обеспечить сериализацию критической операции средствами PostgreSQL.

Например:

- транзакция;
- блокировка строки `installation_setup`;
- повторная проверка состояния внутри транзакции;
- атомарное создание связанных сущностей;
- атомарное завершение установки.

Нужно проверить совместимость подхода с Prisma 7 и используемым PostgreSQL adapter.

## 19.2. Необратимость завершения

После `COMPLETED` обычный код приложения не должен иметь возможность повторно запустить Bootstrap.

Нужно отдельно рассмотреть:

- права роли PostgreSQL, используемой приложением;
- запрет удаления или сброса Installation_Setup;
- защиту от повторного создания OWNER;
- восстановление из резервной копии;
- аварийное восстановление первоначального владельца.

CHECK и UNIQUE INDEX недостаточны для решения всех этих задач.

## 19.3. Состояния Bootstrap

Текущие состояния:

```text
NOT_STARTED
TOKEN_ISSUED
EMAIL_PENDING
COMPLETED
```

Необходимо явно определить разрешённые переходы.

Например:

```text
NOT_STARTED
    ↓
TOKEN_ISSUED
    ↓
EMAIL_PENDING
    ↓
COMPLETED
```

Истечение токена, повторная выдача, отмена регистрации и повторное подтверждение email должны обрабатываться явно.

## 19.4. Сроки действия

- Bootstrap CLI-токен — 15 минут.
- Email-токен — срок необходимо согласовать.
- Временная регистрация — срок необходимо согласовать.

Проверять время по серверному UTC, а не по времени браузера.

## 19.5. Хранение пароля

В Setup_Registration хранится только Argon2id-хеш пароля.

После успешного создания OWNER необходимо определить политику очистки временных регистрационных данных.

Не хранить лишние копии хешей и персональных данных бессрочно.

## 19.6. Тестирование

Нужно проверить минимум:

- первая установка;
- истёкший токен;
- неверный токен;
- повторное использование токена;
- два одновременных запроса;
- истёкшая email-регистрация;
- неправильный email-код;
- превышение лимита попыток;
- повторный запуск CLI;
- попытка создания второго OWNER;
- ошибка транзакции посередине;
- повторная регистрация после COMPLETED;
- восстановление после сбоя процесса.
